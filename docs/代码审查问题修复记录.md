### [P0-001] 安全防御：修复反向代理真实客户端 IP 获取与伪造绕过漏洞
- **问题级别**：P0 阻断性 / 安全加固
- **涉及文件**：[`backend/src/middleware/ipRules.ts`](../backend/src/middleware/ipRules.ts)
- **根本原因**：原代码直接截取 HTTP 请求头中的 `req.headers['x-forwarded-for'].split(',')[0]`，在未经反向代理剥离的情况下，外网攻击者可通过自行伪造 `X-Forwarded-For: 127.0.0.1` 请求头，轻而易举绕过系统的 IP 黑白名单防护。
- **修复方案**：
  1. 使用 Express 经过 `trust proxy` 净化后的 `req.ip` 作为唯一权威的客户端 IP 来源；
  2. 严禁直接信任未经代理剥离的未净化请求头；
  3. 保留对 IPv6 映射的 IPv4 地址（`::ffff:x.x.x.x`）以及本地回环地址（`::1` -> `127.0.0.1`）的标准规范化处理。
- **对应 Git 提交**：
  ```bash
  git commit -m "fix(security): sanitize client IP extraction using trusted req.ip (P0-001)"
  ```

### [P0-002] 部署安全：消除生产环境变量中硬编码的弱 JWT 密钥风险
- **问题级别**：P0 阻断性 / 生产部署安全
- **涉及文件**：[`docker-compose.yml`](../docker-compose.yml), [`backend/src/config.ts`](../backend/src/config.ts)
- **根本原因**：`docker-compose.yml` 中直接硬编码写入了默认弱密钥 `JWT_SECRET: ${JWT_SECRET:-sacred_focus_super_secret_jwt_key_2026}`，若运维人员未在 `.env` 中声明，系统将静默暴露在公网已知签名弱口令下，攻击者可任意伪造管理员 Token。
- **修复方案**：
  1. 在 `docker-compose.yml` 中移除弱密钥默认回退，强制使用 `${JWT_SECRET}` 引用环境变量；
  2. 在 `backend/src/config.ts` 中引入生产环境（`NODE_ENV=production`）强制密钥拦截：
     - 若未配置 `JWT_SECRET`，直接阻止进程启动并输出清晰错误；
     - 维护已知泄露弱密钥黑名单（`BANNED_SECRETS`），若检测到生产环境使用测试弱密钥，立即强制 `process.exit(1)` 拒绝启动。
- **对应 Git 提交**：
  ```bash
  git commit -m "fix(security): enforce strong non-default JWT secret in production mode (P0-002)"
  ```

### [P0-003 & P1-001] 状态机与每日结算：连胜重置同步递增 Revision，保护冷冻节点不被误重置
- **问题级别**：P0 阻断性 & P1 严重 / 核心状态一致性
- **涉及文件**：[`backend/src/db/queries/settlement.ts`](../backend/src/db/queries/settlement.ts)
- **根本原因**：
  1. 跨天自动结算逻辑中，当检测到前一业务日未点亮国策而将主链连胜清零（`currentStreak = 0`）时，未调用 `incrementSystemRevision()`，导致前端 PWA 离线缓存无法感知连胜清零事件；
  2. 每日重置所有国策点亮状态时，使用了 `UPDATE focus_nodes SET isLit = 0`，未对 `isFrozen`（已被冷冻封存）的节点进行排除，破坏了永久冷冻的业务语义。
- **修复方案**：
  1. 在跨天重置所有国策节点时增加条件过滤：`WHERE isLit = 1 AND isFrozen = 0`，确保冷冻封存节点状态不受每日结算影响；
  2. 在每日结算重置节点状态或重置连胜（`streakReset = true`）时，强制调用 `incrementSystemRevision()`，确保全系统版本感知即时生效。
- **对应 Git 提交**：
  ```bash
  git commit -m "fix(settlement): bump revision on streak reset and protect frozen nodes (P0-003, P1-001)"
  ```

### [P1-002] 数据同步：补充漏配的系统版本号自增调用，杜绝静默不同步
- **问题级别**：P1 严重 / 多端数据同步
- **涉及文件**：[`backend/src/routes/focusTree.ts`](../backend/src/routes/focusTree.ts), [`backend/src/routes/evolution.ts`](../backend/src/routes/evolution.ts)
- **根本原因**：系统多端同步依赖全局版本自增（`system_revision`）。但在国策树的核心路由中，以下写操作均遗漏了 `incrementSystemRevision()`：
  - `POST /focus-tree/nodes/:id/toggle-lit`（节点点亮 / 熄灭状态变更）
  - `POST /focus-tree/nodes/reorder`（列表基准重排）
  - `POST/PUT/DELETE /focus-tree/nodes`（节点增删改）
  - `POST/PUT/DELETE /focus-tree/groups`（分组增删改）
  - `POST /evolution/import`（全量数据镜像恢复）
- **修复方案**：
  - 在上述所有涉及国策树结构、属性变更与全量镜像导入的业务逻辑执行成功后，全部补齐 `incrementSystemRevision()` 调用。
- **对应 Git 提交**：
  ```bash
  git commit -m "fix(sync): bump system revision across focus tree mutations and data import (P1-002)"
  ```

### [P1-004] 状态机安全：引入 previousLastLitDate 字段消除悔棋刷分漏洞
- **问题级别**：P1 严重 / 业务逻辑漏洞
- **涉及文件**：
  - [`backend/src/types.ts`](../backend/src/types.ts)
  - [`backend/src/db/schema.ts`](../backend/src/db/schema.ts)
  - [`backend/src/db/migrations.ts`](../backend/src/db/migrations.ts)
  - [`backend/src/db/queries/focusTree.ts`](../backend/src/db/queries/focusTree.ts)
  - [`backend/src/routes/focusTree.ts`](../backend/src/routes/focusTree.ts)
  - [`frontend/src/types/index.ts`](../frontend/src/types/index.ts)
- **根本原因**：原系统在点亮国策时将 `lastLitDate` 更新为当天；取消点亮（`isLit: 0`）时，简单地将 `lastLitDate` 赋为 `NULL`。若用户对前几天曾经点亮过的节点执行“误点 -> 取消”，该节点的历史点亮日期就会被抹除为 `NULL`，破坏了历史记录并可能被利用规避断签惩罚。
- **修复方案**：
  1. 数据库新增 `previousLastLitDate TEXT` 字段，并在启动迁移中自动执行 `ALTER TABLE focus_nodes ADD COLUMN previousLastLitDate TEXT;`；
  2. 在点亮节点时，将旧的 `lastLitDate` 快照备份到 `previousLastLitDate`，再写入新日期；
  3. 在取消点亮时，将 `previousLastLitDate` 的值精确还原回 `lastLitDate`，并重置 `previousLastLitDate = NULL`，确保状态机可逆且无状态遗失。
- **对应 Git 提交**：
  ```bash
  git commit -m "fix(focus-tree): preserve previous last lit date to prevent streak corruption on unlight (P1-004)"
  ```

### [P1-005 & P3-001] 神圣座位：补全页面离开违规上报与强伪随机 Log ID 生成
- **问题级别**：P1 严重 & P3 轻微 / 专注律法与稳健性
- **涉及文件**：[`frontend/src/views/SacredSeatView.vue`](../frontend/src/views/SacredSeatView.vue)
- **根本原因**：
  1. 用户在神圣座位进行专注时，若已过 30 秒后悔药窗口，直接点击浏览器后退或导航离开，前端仅做了提示或本地中止，未向服务端记录 `FAIL` 违规日志并清零连胜，导致自律铁律形同虚设；
  2. 原日志 ID 生成算法采用 `Date.now() + Math.random()`，存在并发碰撞风险。
- **修复方案**：
  1. 在 `onBeforeRouteLeave` 导航守卫中，如果当前处于专注状态且已过后悔药窗口，在用户确认强行离开时，自动构造 `status: 'FAIL'` 会话日志上报服务端，服务端原子重置主链连胜为 0；
  2. 采用标准 `crypto.randomUUID()`（配合时间戳兜底）构建具备强抗碰撞性的全局唯一 Log ID。
- **对应 Git 提交**：
  ```bash
  git commit -m "fix(seat): record fail log on route leave after regret window and use crypto UUID for logs (P1-005, P3-001)"
  ```

### [P2-003] 鉴权性能：登录改为异步 bcrypt 比较，防止 Event-Loop 阻塞
- **问题级别**：P2 一般 / 服务吞吐量与性能
- **涉及文件**：[`backend/src/routes/auth.ts`](../backend/src/routes/auth.ts), [`backend/src/middleware/auth.ts`](../backend/src/middleware/auth.ts)
- **根本原因**：`POST /auth/login` 曾使用同步 `bcrypt.compareSync`，其计算密集耗时（通常 100~300ms），在高并发或密码撞库攻击下会直接卡死 Node.js 单线程事件循环，导致其他专注接口响应延迟暴增。
- **修复方案**：
  1. 路由处理器改为 `async (req, res)`，使用非阻塞的 `await bcrypt.compare(...)`，将哈希工作移交 libuv 线程池；
  2. 在 `/status` 静态信物比对中，统一复用 `middleware/auth.ts` 中导出的常量时间比对函数 `safeCompare`，消除重复实现与潜在时序攻击。
- **对应 Git 提交**：
  ```bash
  git commit -m "perf(auth): use async bcrypt.compare to eliminate event loop blocking and unify safeCompare (P2-003)"
  ```

### [P3-004] 并发版本自增：系统全局版本号改用原子 SQL UPSERT 增量递增
- **问题级别**：P3 轻微 / 并发稳态
- **涉及文件**：[`backend/src/db/revision.ts`](../backend/src/db/revision.ts)
- **根本原因**：原代码通过 JavaScript 先 `SELECT` 读取版本号，在 JS 内存中加 1，再执行 `INSERT OR REPLACE` 写回。当多个不同请求并发触发版本自增时，可能读取到相同旧版本并发生写入覆盖。
- **修复方案**：
  改用 SQLite 原生原子 UPSERT 语法并在内部事务中执行：
  ```sql
  INSERT INTO system_meta (key, value)
  VALUES ('system_revision', '1')
  ON CONFLICT(key) DO UPDATE SET value = CAST(CAST(system_meta.value AS INTEGER) + 1 AS TEXT);
  ```
  彻底杜绝 Node.js 内存读写竞态，确保多并发场景下每次调用版本号必然严格单调自增。
- **对应 Git 提交**：
  ```bash
  git commit -m "perf(db): make incrementSystemRevision atomic using SQL UPSERT (P3-004)"
  ```
